# 开发文档写作：草稿 → 定稿（开发）→ 提测文档

覆盖三个阶段，按用户当前所处阶段执行对应部分，不要一次性全部执行。

**草稿阶段面向开发者，允许出现代码位置；定稿与提测文档面向评审与测试，全文禁止代码位置。**

---

## 零、内容硬纪律（适用于所有阶段，写完必须过 Gate 自检）

### D1 影响面 = 业务逻辑串联，禁止代码位置

技术方案与提测文档**全文**——包括正文、表格、架构图节点、流程图节点——禁止出现：

- 文件路径 / 文件名（如 `qc_job_list.go`、`internal/data/...`）
- 函数 / 方法 / struct / 变量名
- proto 字段号（如 `label_tag_mode = 17`）
- 行号、SQL 片段里的实现细节

影响面必须按以下六个维度**逐项排查**（排查过但无影响的，明确写「无」，不许静默跳过）：

| 维度 | 必须写清 |
|---|---|
| 接口 | 完整路径（如 `POST /api/qc/v1/jobs`）+ 行为变化（新增参数 / 返回变化 / 行为差异）。同族接口必须排查齐全：列表与 count、主路径与回退路径、新旧版本接口 |
| MQ | topic + 消息体字段路径 + 生产方 / 消费方 + 消息语义变化 |
| RPC | 服务名 + 方法名 + 请求 / 响应字段变化 + **所有调用方**（含其他服务） |
| 定时任务 | 任务名 + 频率 + 行为变化 |
| 配置 | 配置文件名 + key 全路径 + 新旧取值语义 |
| 数据库 | `库.表.字段` 全限定；嵌套 JSON 字段写到 `表.字段.子字段` |

典型错误：只写了列表接口，漏了统计 count 接口；只写主流程，漏了 RPC 不可用时的本地回退路径；两个服务有同构实现（本地 SQL + 下沉 DAO 服务），只改了一边。

### D2 信息源纪律：代码内文档默认不可信

- 代码注释、README、代码目录里的遗留设计文档**默认过时、默认错误**，禁止直接采信为事实依据。
- 可信事实源只有：**代码本身**（proto / 接口定义与路由注册、实际 SQL、config 结构体与默认值）、数据库实际表结构、运行中的配置。
- 如果某处代码内文档是理解的关键线索，**必须先用 ask_user_question 向用户确认**「XX 处的注释/文档是否仍然准确」，用户确认前不得作为依据写入文档。
- 代码内文档与代码事实冲突时，以代码为准，并在文档或回复中提示用户「XX 注释与实际代码不符，已按代码为准」。

### D3 字段与配置必须全链路、全限定

- 数据库：`库.表.字段`；JSON 嵌套字段：`表.字段.子字段.孙字段`。
- 业务 / proto 字段：`所属接口或 Message.field`，不许裸写 `label_tag_mode` 这种半截名。
- 配置：`配置文件名 → key 路径`（如 `data-service.yaml → qc.collect_dao.enabled`）。
- MQ：`topic → 消息体字段路径`。
- **写不全时必须停下来集中提问**（用 ask_user_question 一次性问齐）：具体哪个库哪张表哪个字段、哪个配置文件哪个 key、哪个 topic、哪个接口全路径。禁止编造、禁止留半截链路、禁止用「某字段」「相关配置」糊弄。

### D4 精炼突出重点

- 骨架沿用 vault 模板，但**按变更范围裁剪**：与本次变更无关的章节整节删除，不留空模板节（无缓存变更就删缓存设计，无新表就删建表 SQL 节）。
- 方案开头必须有「一页结论」callout：目标一句话 + 改了什么（业务语言，三五条）+ 最关键的影响与风险。
- 每个小节用三五句话或一张表讲完，不复述需求背景、不堆砌实现细节论证。
- 详细设计里只展开**有变化的部分**，没变的现状一笔带过或引用现网行为。

### D5 架构与流程必画图

- 技术方案必须至少包含：一张**架构 / 数据流图**（服务、接口、topic、库表之间的拓扑）+ 关键链路的**流程或时序图**。缺图视为未完成。
- 图节点必须是业务元素：服务名、接口路径、topic 名、表名、配置 key。禁止文件名 / 函数名。
- 默认用 Mermaid（Obsidian 原生渲染，便于评审时直接看）；用户要求精修、或方案定稿归档时，可调用 excalidraw-diagram skill 出精修版（.excalidraw / .svg / .png）并嵌入文档。

### D6 测试要点 = 全量受影响场景回归

- 测试要点必须**从影响面分析逐条推导**：D1 排查出的每个接口行为变化、每条 MQ 消息变更、每个字段 / 配置变更，都要有对应回归项，一一对应，不许只测新增功能。
- 必须显式覆盖：
  - **兼容性回归**：不传新参数 / 旧调用方，行为与现网完全一致；
  - **口径一致性**：同族接口（列表 vs count、本地路径 vs RPC 回退路径）结果一致；
  - **全量受影响接口清单**：逐个列出要求回归的接口与业务场景，而不是一句「回归相关接口」。

### Gate：产出前自检（任一不满足必须返工）

- [ ] 全文（含 mermaid 图）搜索无 `.go` / `.py` / `.ts` / `internal/` / `func ` 等代码位置命中
- [ ] D1 六个维度都排查并写明（含「无」）；同族接口、回退路径、其他调用方都覆盖
- [ ] 所有字段都是全限定链路，无裸字段名、无「某字段 / 相关配置」
- [ ] 引用的每条代码内注释 / 遗留文档都经过用户确认
- [ ] 架构图 + 流程图存在，节点全是业务元素
- [ ] 测试要点与影响面逐条对应，含兼容性回归与口径一致性
- [ ] 模板无关章节已裁剪，无空节；开头有一页结论

## 环境确认（首次使用必须问，禁止硬编码）

本 skill 不内置任何本机路径。每个会话首次使用时：

1. 先读环境配置文件 `~/.pi/agent/dev-doc.env.md`。
2. **存在** → 直接使用其中的路径，不再追问。
3. **不存在** → 用 ask_user_question 一次性向用户确认以下项，并把结果写入该文件供后续会话复用：
   - Obsidian vault 基路径（可用 `obsidian eval code="app.vault.getName()"` 探测 vault 名辅助确认）
   - 草稿 / 技术方案 / 提测文档的目录名（默认建议：`草稿/`、`技术方案/`、`自测文档/`，用户可自定义）
   - 技术方案模板、提测文档模板的笔记路径（默认在 vault 内找，找不到就问用户要路径）
   - 代码仓库根目录（多个服务仓库的父目录）
   - 其他环境特有约定（如已废弃的旧目录）
4. 使用中遇到路径不存在、找不到文件、配置里没覆盖的情况：**停下来问用户**，禁止猜测、禁止把某个路径当作理所当然写进文档。

下文中的 `草稿/`、`技术方案/`、`自测文档/` 均指环境配置中确认的目录名。

git/MR 信息一律从仓库实际命令推导，不要写死托管平台：

- MR 基础链接 = `git remote get-url origin` 的结果去掉 `.git` 后拼 `/-/merge_requests/<iid>`
- MR 编号优先用平台 CLI（如 `glab mr list -R <group>/<repo> --source-branch=<分支>`）查询；CLI 不可用或查不到时问用户，禁止编造

### 工具选择原则

- **读/搜索/移动/属性**：优先用 `obsidian` CLI（`obsidian read`、`obsidian search`、`obsidian move`、`obsidian property:set`）。`obsidian move` 会自动更新反链，不要直接 `mv`。
- **写大段内容**：CLI 的 `content=` 需要 `\n` 转义，长文档不适用。直接用 write 工具写 vault 基路径下的绝对路径，Obsidian 会自动感知新文件。已存在的文件先 `obsidian read` 再编辑。

## 阶段一：新建技术方案草稿（面向开发者，允许代码位置）

在 `草稿/` 下创建笔记，文件名用需求短标题。

frontmatter 固定格式：

```yaml
---
title: <完整标题，可含服务名前缀>
date: YYYY-MM-DD
tags:
  - todo
  - <服务名，如 data-service>
  - <领域，如 job / qc / dispatch>
status: todo
---
```

正文结构约定：

1. `# <标题>`，紧跟 `> [!summary] 目标` callout 用一两句话写目标。
2. `> [!important] 当前代码基线` callout：先实际读代码确认已有能力（用 rg / read / sgrep），明确「已存在什么、还缺什么」，避免方案里重复新增同义字段。**不要凭空写基线，必须查代码**；基线结论只能来自代码本身，代码内注释按 D2 处理。
3. 正文按模块分节，待办用 `- [ ]` checkbox，精确到文件/函数/字段/SQL（草稿阶段允许且应该精确）。
4. **每个 checkbox 后面标注它对应的业务影响面条目**（如「→ `POST /api/qc/v1/jobs` 新增 label_tag_mode 入参」「→ collect-dao `QryCountQCJobs` RPC 新增字段，调用方仅 data-service」），为定稿阶段翻译成业务语言做准备。
5. 影响面按 D1 六维度排查一遍，排查结果直接写进草稿（哪些接口 / topic / RPC / 配置 / 表受影响），不确定的当场问用户。
6. 需要澄清的需求点单独列出，标注「最终值需冻结」「需确认映射」等风险提示。

## 阶段二：草稿 → 定稿（开发）

1. 迁移：`mkdir` 目标年月目录后 `obsidian move path="草稿/<文件>.md" to="技术方案/<当前年月，如 2026-10>"`，文件名改为 `<标题>技术方案.md`。
2. 内容按「面向评审的方案文档」重写：
   - **先做翻译**：把草稿里所有代码位置条目翻译成业务语言（接口路径、服务+方法、topic、库.表.字段），翻译不出来的（说不清对应哪个接口/topic/表）说明影响面没查全，回去补查或问用户；
   - 骨架取技术方案模板（路径来自环境配置），按 D4 裁剪无关章节；开头加「一页结论」callout；
   - 接口清单写完整路径；DB 变更写 `库.表.字段`；MQ / RPC / 配置按 D1 表格口径写全；
   - 按 D5 画架构图与核心流程图（Mermaid）；
   - 测试要点按 D6 从影响面逐条推导；
   - 状态标识：标题下 blockquote 列 **状态 / 适用服务 / 涉及接口**，或 frontmatter `status: design`，与目录现有文档保持一致。
3. 归档：需求上线或彻底关闭后 `obsidian move path="技术方案/<年月>/<文件>.md" to="技术方案/归档/<该文件原年月>"`。
4. 定稿前后各跑一次 **Gate 自检**。

## 阶段三：生成开发提测文档

产物：`自测文档/开发提测文档-<JIRA编号>-<需求标题>.md`。

### 内容来源（按此顺序采集，缺失项先问用户，不要编造）

1. **模板结构**：`obsidian read path="<提测文档模板路径>"`（模板路径来自环境配置），复制七大节（基础信息 / 提测内容 / 测试指引 / 依赖与风险 / 开发自测情况 / 附件 / 备注）。模板里 Pipeline 链接的拼写照抄。
2. **关联技术方案笔记**：`obsidian search query="<需求关键词>"` 找 `技术方案/` 和 `草稿/` 下的相关笔记，提取：
   - 需求背景 → §2.1（含 Jira 单号和 PRD 链接时写入 §一 基础信息）
   - 改造点清单 → §2.2 功能清单（功能点 / 说明 / P0~P2）
   - **影响面（D1 六维度）** → §2.3 改动范围：后端接口（全路径，一行一个 `<br>`）、数据库变更（库.表.字段）、配置变更（文件 → key）、第三方依赖（服务+方法 / topic）
   - 明确不做的部分 → §2.4 本次不包含内容
3. **git 仓库信息**：确认涉及服务仓库（在环境配置的仓库根目录下，不确定就问用户）后执行：
   ```bash
   git -C <repo> branch --show-current
   git -C <repo> remote get-url origin
   git -C <repo> log --oneline origin/main..HEAD 2>/dev/null || git -C <repo> log --oneline -10
   glab mr list -R <group>/<repo> --source-branch=<分支>
   ```
   MR 链接 = `<origin url 去掉 .git>/-/merge_requests/<iid>`；Pipeline 链接为 MR 合并后的 `/-/pipelines/<id>`。glab 不可用或查不到 MR 编号时问用户，不要编造。
4. **对话中提供**：提测人、提测日期、预计测试周期、Jira/PRD 链接、提测环境、测试重点、已知问题。信息不全时集中一次性询问用户，仍缺的在表格中留空。

### 填写规范

- 不确定的字段**留空**，禁止编造测试账号、覆盖率、自测结果。
- §三 测试指引必须按 D6 写：全量受影响接口与业务场景逐条列出回归项，含兼容性回归与口径一致性，不许只写新增功能。
- §2.3 改动范围禁止出现代码位置（文件/函数名），一律业务语言。
- 提测文档创建后，关联草稿笔记用 `obsidian property:set name="status" value="done" path="草稿/<文件>.md"` 更新（或按用户要求归档）。
- 创建完成后输出文件完整路径，并提醒用户补齐测试环境信息（§3.1 通常由测试/用户填写）。
- 产出前跑 **Gate 自检**。

## 快速命令参考

```bash
obsidian search query="<关键词>" limit=10            # 找笔记
obsidian read path="草稿/<文件>.md"                    # 读笔记
obsidian move path="草稿/<文件>.md" to="技术方案/2026-10"  # 迁移（自动更新反链，目录需先 mkdir）
obsidian property:set name="status" value="done" path="草稿/<文件>.md"
```
