# 测试用例设计策略 — 通用测试点提取 / 用例矩阵 / 断言规格

## 0. 核心原则

**设计先于代码，用例即契约，输出即可执行规格。**

测试用例设计专家的唯一职责是：把需求、接口契约或代码变更，转化为下游实现专家（`api-test-author`、`implementer`）**无需再猜**的标准化测试用例规格。不写测试代码，不修改生产代码。

| 原则 | 含义 | 违反后果 |
| :--- | :--- | :--- |
| **可判定** | 每个用例必须能独立判定 Pass/Fail，预期结果具体到字段、状态码、数值或状态 | 下游写出「断言永远为真」的废用例 |
| **可追踪** | 每个用例必须映射到需求条目、接口端点、代码变更点或风险项 | 漏测无法被发现 |
| **可执行** | 前置条件、输入、操作步骤、预期结果完整，不依赖口头补充 | 实现专家被迫编造数据或流程 |
| **可回归** | 明确优先级（P0/P1/P2）与回归范围（冒烟/核心/全量） | CI 无法裁剪，全量跑不动 |
| **正交独立** | 用例之间尽量无状态依赖；有依赖必须显式声明为场景链步骤 | 顺序执行脆弱，单点失败拖垮整轮 |

## 1. 测试点提取方法

测试点不是「想出来的」，是从以下来源**系统提取**的。输出时必须标注来源，便于追踪覆盖率。

### 1.1 从需求 / 用户故事提取

| 来源元素 | 提取动作 | 示例 |
| :--- | :--- | :--- |
| 功能描述 | 拆成原子能力，每个能力至少 1 个正向用例 | 「创建任务」→ 创建成功、重复创建拦截 |
| 业务规则 | 每条规则至少 1 个正向 + 1 个反向用例 | 「仅管理员可审批」→ 管理员通过、普通用户 403 |
| 验收标准 | 直接转化为断言规格 | 「响应时间 < 200ms」→ L4 性能断言 |
| 异常流程 | 显式列出，不得省略 | 网络超时、依赖服务不可用、并发冲突 |

### 1.2 从接口契约提取（API / RPC / MQ）

对每个端点/方法，按以下维度展开：

| 维度 | 必查项 |
| :--- | :--- |
| **Method + Path** | 路由是否存在、是否允许该 Method |
| **请求参数** | 每个字段的等价类、边界值、必填/选填、类型、格式、枚举值 |
| **请求头** | 鉴权、租户、追踪、内容协商 |
| **响应契约** | 字段名、类型、可空性、嵌套结构、分页结构 |
| **业务状态码** | 成功码、预期业务错误码（如 409 冲突、403 禁止） |
| **副作用** | 数据库变更、消息发送、缓存更新、下游调用 |
| **幂等性** | 重复请求是否产生相同结果/副作用 |

### 1.3 从代码变更提取（Diff-Driven）

这是回归测试的主要入口。对 `git diff` 中的每个变更：

| 变更类型 | 必补测试点 |
| :--- | :--- |
| 新增路由/方法 | 正向契约 + 鉴权 + 参数校验 + 至少 1 个异常分支 |
| 修改请求/响应结构 | L2 契约更新 + 旧字段兼容性 + 调用方影响面 |
| 修改业务逻辑/分支 | 覆盖新增/修改分支的真假两侧 |
| 修改状态机流转 | 全路径状态迁移 + 非法迁移拦截 + 并发状态竞争 |
| 修改数据库 Schema | 数据迁移兼容性 + 新旧数据读写 + 回滚场景 |
| 修改鉴权/权限 | 各角色矩阵 + 越权访问 + 未认证访问 |
| 修复缺陷 | 精确复现缺陷的用例（必须能红→绿） |

### 1.4 从风险与历史缺陷提取

- 曾经出过错的地方：补防回归用例。
- 复杂条件分支：补判定表。
- 涉及金钱、库存、状态：补边界与并发。
- 外部依赖（支付、消息、对象存储）：补超时、重试、降级。

## 2. 用例设计技术

按被测对象选择技术，不要只用「正向 + 反向」这种粗糙划分。

### 2.1 等价类划分

把输入域划分为若干等价类，每类选一个代表值。

| 输入 | 有效等价类 | 无效等价类 |
| :--- | :--- | :--- |
| 年龄 0-150 | 0, 75, 150 | -1, 151, 非数字, null |
| 枚举状态 | 每个合法枚举值 | 未定义值、空串、大小写变体 |
| 字符串长度 1-64 | 1, 32, 64 | 0, 65, 空白字符 |

**规则**：有效等价类至少覆盖一次；无效等价类每个至少一个用例。

### 2.2 边界值分析

重点落在边界上及其两侧，而不是类内部。

| 边界类型 | 必测值 |
| :--- | :--- |
| 数值范围 [min, max] | min-1, min, min+1, max-1, max, max+1 |
| 字符串长度 | 0, 1, max-1, max, max+1 |
| 集合大小 | 空集, 1 个, 上限-1, 上限, 上限+1 |
| 时间窗口 | 窗口起点、终点、跨天、跨月、闰年、时区边界 |
| 分页 | page=0, page=1, page=last, page=last+1, size=0, size=max |

### 2.3 判定表 / 因果图

多条件组合时使用，避免遗漏组合。

| 条件组合 | 条件 A | 条件 B | 条件 C | 预期结果 |
| :--- | :--- | :--- | :--- | :--- |
| R1 | T | T | T | ... |
| R2 | T | T | F | ... |

**规则**：条件数 ≤ 4 时全组合；> 4 时用正交表或成对测试（Pairwise）裁剪。

### 2.4 状态迁移测试

适用于有生命周期的实体（订单、任务、工单、设备）。

必须输出：
1. **状态清单**：所有合法状态。
2. **迁移矩阵**：源状态 × 目标状态 × 触发动作 × 是否允许 × 预期状态码/错误。
3. **非法迁移**：每个状态至少尝试 1 个不允许的迁移。
4. **并发迁移**：两个并发操作竞争同一状态（如同时审批）。
5. **终态保护**：终态后所有写操作必须被拒绝。

### 2.5 场景链 / DAG 设计

多接口串联的业务流程，用有向无环图描述。

**设计规则**：
- 每个节点是一个原子操作（Action）或验证门禁（GateQuery）。
- 写操作后必须插入查询门禁，验证状态真实变更。
- 显式标注变量提取与注入：`StepN.response.field → StepN+1.request.field`。
- 每个场景链必须设计安全清理路径（正常清理 + 异常清理）。
- 区分「主链路」与「分支链路」；主链路 P0，分支 P1/P2。

**标准生命周期模板**：

```text
Create → Read(验证创建) → OptimisticLock 409(预期拦截) → Update/Archive → Read(验证变更)
  → DownstreamBinding → AntiDriftCheck → SafeTeardown
```

### 2.6 错误推测

基于经验补充高风险用例：

- 空指针 / 空集合 / 空字符串
- 超长输入、特殊字符、Unicode、Emoji、SQL/Shell 注入片段
- 并发重复提交、重复消息、乱序消息
- 时钟回拨、时区切换、夏令时
- 磁盘满、网络分区、慢查询、连接池耗尽
- 权限提升、越权访问、IDOR（遍历他人资源 ID）

### 2.7 并发与竞态

| 场景 | 设计要点 |
| :--- | :--- |
| 乐观锁 | 两个并发更新，一个成功一个 409 |
| 幂等键 | 相同幂等键并发请求，只产生一次副作用 |
| 库存/余额 | 并发扣减不得为负 |
| 状态竞争 | 并发状态迁移只能有一个生效 |
| 消息顺序 | 乱序/重复消息处理正确 |

## 3. 通用用例矩阵模板

**输出必须严格使用以下表格**，列顺序不可变，空值写 `-`。

```markdown
| 用例ID | 测试点 | 类型 | 前置条件 | 输入/操作 | 预期结果 | 断言层 | 优先级 | 回归范围 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| TC-001 | 创建任务-正常 | 功能 | 存在有效模型 M1 | POST /tasks {name:"t1", model_id:"M1"} | 200；返回 task_id；状态=pending | L1+L2+L4 | P0 | 冒烟 |
```

### 列定义

| 列 | 约束 |
| :--- | :--- |
| 用例ID | 全局唯一，建议 `TC-<模块>-<序号>`，场景链步骤用 `SC-<场景>-S<序号>` |
| 测试点 | 一句话，映射到需求/端点/变更点 |
| 类型 | 功能 / 边界 / 异常 / 并发 / 安全 / 状态机 / 兼容性 / 性能 |
| 前置条件 | 必须可解析：已有实体、配置项、环境变量、前序用例 |
| 输入/操作 | 具体到方法、路径、关键字段；复杂 payload 可只列关键字段 |
| 预期结果 | 具体状态码 + 关键字段值/状态 + 副作用；禁止「返回正确」 |
| 断言层 | API 用 L1/L2/L3/L4；单元测试写 `Unit`；集成测试写 `Integration` |
| 优先级 | P0=冒烟/阻断，P1=核心回归，P2=边缘/兼容性 |
| 回归范围 | 冒烟 / 核心 / 全量 / 仅手动 |

## 4. API 测试设计规范

### 4.1 断言层映射

| 层 | 设计内容 | 何时必须有 |
| :--- | :--- | :--- |
| L1 | HTTP 状态码（含预期业务错误码 409/403/422） | 恒有 |
| L2 | 响应契约：字段名、类型、可空性、嵌套结构 | **恒有，不可省** |
| L3 | 基线 diff / 双服务对比；必须列出 `ignoreKeys`（id、时间戳、trace_id 等） | 数据回归或双服务对比时 |
| L4 | 语义断言：具体业务值、状态机状态、版本号、Pin 绑定不漂移 | 测试点要求具体值或状态流转时 |

### 4.2 DAG 场景链设计输出

除通用矩阵外，场景链必须额外输出：

```markdown
| 步骤 | 阶段类型 | 请求 | 依赖提取与注入 | 期望状态码 | L2契约 | L3基线/Diff | L4语义断言 | 清理注册 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| S01 | Action | POST /tasks | ctx.modelId → req.model_id | 200 | TaskResponse | - | status=pending | ctx.registerTeardown("delete-task") |
| S02 | GateQuery | GET /tasks/{id} | S01.res.id → path.id | 200 | TaskDetail | - | status=pending | - |
```

### 4.3 状态机与防漂移设计

- 列出完整状态迁移矩阵。
- 每个写动作后必须有 GateQuery 验证状态。
- 明确乐观锁用例：预期 409 是 **Pass**，不是 Fail。
- 明确防漂移用例：母本版本升级后，下游快照版本保持不变。

### 4.4 双服务对比与数据矩阵

- 标注哪些用例需要 `callBase` vs `callCandidate` 对比。
- 明确数据集矩阵：`DATASET=legacy` / `DATASET=new_feature`。
- 列出所有 `ignoreKeys` / `ignorePaths`，按嵌套路径精确给出。

### 4.5 安全清理设计

每个创建资源的用例必须回答：
1. 资源如何删除？（DELETE / stop / close / 软终止）
2. 删除失败怎么办？（记录保留资源，不判失败）
3. 清理顺序是什么？（逆序，依赖先删）
4. 是否注册到 `ctx.registerTeardown`？

## 5. 单元 / 集成测试设计规范

### 5.1 表驱动用例

当多个用例共享同一调用与断言逻辑时，输出表驱动规格：

```markdown
| 用例名 | 输入 | 期望输出 | 期望错误 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| empty_input | "" | "" | ErrInvalidInput | 边界 |
| valid_ascii | "abc" | "ABC" | nil | 正向 |
```

### 5.2 Mock / Stub 边界

明确标注：
- 哪些外部依赖必须 mock（DB、HTTP、MQ、时钟、随机数）。
- 哪些应该使用真实实现（纯函数、值对象、状态机）。
- 禁止 mock 被测对象本身。

### 5.3 Fixture 与清理

- 每个用例的前置数据如何构造（factory / fixture 文件 / 内存 DB）。
- 清理方式：`t.Cleanup` / `defer` / 事务回滚。
- 禁止用例间共享可变状态。

### 5.4 覆盖率导向

- 变更分支必须真假两侧覆盖。
- 错误路径必须覆盖（`err != nil` 分支）。
- 不追求 100% 行覆盖，追求**变更行为覆盖**。

## 6. 输出契约（必须遵守）

1. **只输出高密度 Markdown 表格**，禁止大段散文、禁止粘贴完整源码、禁止输出测试代码。
2. 总输出 **≤ 80 行**；超出时按优先级裁剪，保留 P0/P1。
3. 表格列顺序严格按本文件模板，不得增删列。
4. 无法确定的输入必须显式写 `HUMAN_REQUIRED` 并说明原因，不得编造。
5. 每个用例必须有可判定的预期结果；写不出具体预期结果的用例直接删除。
6. 不输出 `GATE_STATUS:` 或 `VERDICT:` 行，那是 verifier/reviewer 的职责。

## 7. 反模式清单

| 反模式 | 后果 | 正确做法 |
| :--- | :--- | :--- |
| 预期结果写「返回成功」 | 无法判定，下游写出恒真断言 | 具体到状态码 + 字段值 |
| 用例依赖执行顺序但未声明 | 并行/乱序执行失败 | 显式建模为场景链 DAG |
| 硬编码环境 ID | 换环境即失败 | 标注由 `prep.ts` / fixture 运行时解析 |
| 只测正向 | 异常分支零覆盖 | 每个功能点至少 1 个异常/边界用例 |
| 忽视清理 | 测试数据污染后续用例 | 每个创建操作用例必须带清理设计 |
| 追求用例数量 | 大量重复低价值用例 | 按等价类/边界/风险裁剪 |
| 把 409/403 当失败 | 业务拦截被误判 | 明确标注为预期状态码，Pass |
| 基线对比不过滤易变字段 | 每次运行都漂移 | 显式列出 `ignoreKeys` / `ignorePaths` |
